# Plan: Task 6b — `use CcxtOcx` Exchange-Scope Entrypoint

**Status**: Ready for implementation (dependency Task 6 "Declarations" is done; `nimble_options` already in `mix.exs`).

**Goal (from tasks.toml)**: The single user-facing macro that gates all per-exchange code generation so consumers only pay the compile-time and memory cost for the exchanges they actually use.

## Context & Constraints

- Active milestone: **v0.1** (first usable data-plane).
- This is the *only* public entrypoint macro in v0.1. Everything else (`defunified`, `defexchange`, typed structs) is internal to the generation or will be called from inside the modules this macro creates.
- Three supported modes (must all work):
  1. `use CcxtOcx, exchanges: [:binance, :okx, :deribit]`
  2. `use CcxtOcx, tier: :tier1` (delegates to `CcxtOcx.Tiers.members_for_tier/1`)
  3. `use CcxtOcx, exchanges: :all`
- **Open policy decision** (must be settled in this task): bare `use CcxtOcx` (no opts)?
  - **Recommended (and chosen for this plan)**: **Option A** — hard compile error with a clear message directing the user to declare `exchanges:` or `:all`. This makes the cost explicit on day one and prevents accidental "I just wanted one exchange but got 100+" surprises.
- NimbleOptions is the mandated schema validator (see `~/.claude/includes/development-philosophy.md` "Cite Ecosystem Precedents").
- Compile-time JS probing pattern already exists (`CcxtOcx.Tiers.Compile`, `BundleSurface.Compile`, `declarations/compile.ex`): boot a short-lived `QuickBEAM` with `:browser` APIs, apply stubs, load the bundle, do work, `stop` in `after`.
- Per-exchange capability data (`has`, `urls`, `timeframes`, `defaultType`) will be needed by Task 9 (`defexchange`). Task 6b should establish the caching location and a small helper so Task 9 does not duplicate the probing logic.
- The generated per-exchange modules (`CcxtOcx.Binance`, `CcxtOcx.Deribit`, …) must be real, documented Elixir modules that later tasks can enrich with `defunified` / `defexchange` calls or `use` a common base.

## Non-Goals / Out of Scope for 6b

- Actual method implementations (`fetch_ticker`, `create_order`, etc.) — those are Task 7.
- Per-exchange struct emission / capability table emission — Task 9.
- Typed return structs (`Ticker`, `OrderBook`, …) — Task 8.
- Any runtime call sites or pools (except the minimal compile-time probing we already know how to do).
- WS / streaming surface.
- Native-Elixir adapters (Phase 7).

## Proposed Module & File Layout

```
lib/ccxt_ocx.ex                 # becomes the real home of `defmacro __using__/1`
lib/ccxt_ocx/
  macros/
    use.ex                      # (new) NimbleOptions schema + resolution + expansion logic
    exchange_caps.ex            # (new) small helper: probe + cache "has/urls/timeframes" for one exchange
  generated/                    # (new, gitignored) — optional future home for on-disk generated modules if we ever move away from pure in-macro defmodule
```

For v0.1 we keep everything inside the `__using__` expansion (pure macro, no extra compiler phases). This matches the "macro-first" philosophy.

`CcxtOcx` itself stays the documentation / telemetry namespace; the `use` is the only behavioural addition.

## NimbleOptions Schema (to be defined in `CcxtOcx.Macros.Use`)

```elixir
@schema NimbleOptions.new!(%{
  exchanges: [
    type: {:or, [{:list, :atom}, {:in, [:all]}]},
    doc: "Explicit list of exchange ids (as atoms) or :all"
  ],
  tier: [
    type: {:in, [:tier1, :tier2, :tier3, :dex]},
    doc: "Shortcut for the corresponding CcxtOcx.Tiers.members_for_tier/1 set"
  ]
})
```

Validation rules (in addition to schema):
- Exactly one of `exchanges` or `tier` may be present (or neither → error per Option A).
- When `exchanges: :all`, emit a loud `@moduledoc` warning on every generated module and on the calling module.
- Unknown exchange ids → compile error with closest-match suggestion (use `String.jaro_distance` or similar against the known list from `BundleSurface.unified_methods` or a cached exchange id list).

## Expansion Strategy (the heart of the plan)

In `CcxtOcx.__using__/1`:

1. Validate opts with NimbleOptions → raise `CompileError` on bad input (excellent error messages are part of the task).
2. Resolve the final list of exchange ids (atoms, lowercased, validated against CCXT's known list).
3. For the calling module, record the chosen scope in a module attribute (`@ccxt_ocx_scope`) so later `defunified` calls inside the same module can see it (defensive; primarily we emit the modules directly).
4. For **each** resolved exchange id:
   - Compute the Elixir module name: `Module.concat(CcxtOcx, Macro.camelize(to_string(id)))`
   - Emit (via `quote` + `unquote`):
     ```elixir
     defmodule unquote(module_name) do
       @moduledoc """
       Generated by `use CcxtOcx, exchanges: [#{inspect(id)}]`.

       Source of truth for this exchange's surface lives in
       `CcxtOcx.Declarations` + the committed `priv/ccxt_surface.exs`.
       """
       # TODO(Task 9): replace with real defexchange :binance (or whatever)
       # For now we emit a minimal stub so the module exists and can be
       # `alias`d / `require`d immediately after the `use`.
       def __exchange_id__, do: unquote(id)
       def __generated_by_task_6b__, do: true
     end
     ```
5. After emitting all per-exchange modules, emit a small "registry" or helper on the calling module (or on `CcxtOcx` itself) so that code can ask "which exchanges did this `use` bring in?" — useful for Task 7's capability-gated emission.

Because `defmodule` inside a macro expansion runs at the call site of `use`, the modules become real, first-class, documented modules in the BEAM for that compile. This is the pattern used by many declarative macro libraries.

## Compile-Time Probing & Caching (shared with Task 9)

Task 6b should introduce the helper that Task 9 will later call:

```elixir
# lib/ccxt_ocx/macros/exchange_caps.ex (new)
defmodule CcxtOcx.Macros.ExchangeCaps do
  @doc """
  Returns (and caches to priv/exchange_caps/<id>.exs) the live capability map
  for one exchange: has, urls, timeframes, options.defaultType, etc.

  Uses the same throwaway QuickBEAM pattern as Tiers.Compile.
  The file is an Elixir term that Task 9's defexchange can `Code.eval_file` or
  `Code.compile_file` at compile time.
  """
  def fetch_or_build(id) :: map()
end
```

Cache location: `priv/exchange_caps/<id>.exs`

The manifest / verification pipeline (`mix ccxt.verify_bundle`) should eventually also refresh these caps files (or at least diff them). For 6b we just need the probing primitive.

## Default-Policy Decision (settled here)

We implement **Option A**:

```elixir
if opts == [] or (not Keyword.has_key?(opts, :exchanges) and not Keyword.has_key?(opts, :tier)) do
  raise CompileError,
    description: """
    `use CcxtOcx` requires explicit scope.

    Choose one:

        use CcxtOcx, exchanges: [:binance, :deribit]
        use CcxtOcx, tier: :tier1
        use CcxtOcx, exchanges: :all     # heavy — you almost certainly don't want this

    See the module docs for guidance on choosing between an explicit list and a tier.
    """
end
```

Document the rationale in the moduledoc of `CcxtOcx`.

## Pre-Implementation Validation Steps (Tidewave Dogfooding — mandatory)

Before writing any macro code, the implementer **must** perform the experiments called out in the task body:

1. Start a Tidewave session (`iex -S mix tidewave`).
2. Using the existing `CcxtOcx.Runtime` + the "define + call" pattern from `docs/tidewave_examples.md`, measure baseline memory for a runtime that only loads Deribit (complex options surface) vs one that loads "everything".
3. Prove that `new ccxt.deribit()` + a few complex calls (fetchOptionChain, fetchPositions, etc.) succeeds in a narrowly scoped runtime.
4. Capture the delta (RSS / JS heap) and attach the numbers + repro script to the task as "evidence that scoping is worth the macro complexity".

Only after the memory/CPU win is quantified do you write the macro.

## Implementation Order (within the task)

1. Add the NimbleOptions schema + resolution helpers (pure, testable).
2. Implement the minimal `__using__` that does nothing but validate + raise on bare use (the policy decision).
3. Add the `exchange_caps` probing helper + file writer (re-uses the browser-stub + load pattern from `tiers/compile.ex`).
4. Extend the macro to emit the per-exchange `defmodule` stubs for a small hard-coded list (e.g. `[:binance, :deribit]`).
5. Generalize to the three input modes, using `CcxtOcx.Tiers` for the tier case.
6. Add excellent error messages + closest-match suggestions.
7. Write unit tests for the resolver and schema (no JS needed).
8. Write an integration test that does `use CcxtOcx, exchanges: [:deribit]` in a test support module and asserts the module `CcxtOcx.Deribit` now exists and responds to `__exchange_id__/0`.
9. Run the full gate (`mix test.json`, dialyzer, credo --strict, `mix compile --warnings-as-errors`).
10. Update `CLAUDE.md` / `ROADMAP.md` / `CHANGELOG.md` (per task-completion rules).

## Acceptance Criteria (lifted + expanded from task)

- `use CcxtOcx, exchanges: [:binance, :deribit]` compiles and defines `CcxtOcx.Binance` + `CcxtOcx.Deribit`.
- `use CcxtOcx, tier: :tier1` brings in the full Tier-1 member set (including variants).
- `use CcxtOcx, exchanges: :all` works but emits loud documentation warnings.
- Bare `use CcxtOcx` produces a clear, actionable `CompileError`.
- Unknown exchange id produces a helpful error (with suggestions).
- The macro is validated by NimbleOptions; adding a new knob later requires touching the schema.
- Memory-delta experiment from the Tidewave dogfooding section is recorded (numbers + repro) either in the task body or as a comment in the implementation.
- All existing quality gates pass (coverage, dialyzer 0 warnings, credo strict, doctor, etc.).
- The plan artifact itself is updated with "implemented" notes when the task is marked done.

## Risks & Mitigations

- **Macro hygiene / module redefinition on recompiles**: Mitigate by making the emitted `defmodule` idempotent or by using `Module.create/3` with `:replace` where appropriate. Document the chosen approach.
- **Long compile times when someone does `:all`**: The warning + the explicit "you pay for this" design is the mitigation. We do not try to make `:all` fast.
- **Cache invalidation on CCXT bump**: The `@external_resource` already present on `declarations.ex` and `tiers.ex` will be mirrored on the caps cache reader. The verify-bundle Mix task will be extended (in a follow-up) to refresh caps.
- **Name collisions in generated modules**: Exchange ids in CCXT are unique and safe as Elixir atoms after camelization. We still validate and raise if the resulting module name would collide with something we already defined.

## Handoff to Later Tasks

After 6b, Task 7 (`defunified`) and Task 9 (`defexchange`) will be written so that they can be **invoked from inside the per-exchange modules** that 6b emits, or they will be called by 6b's expansion on behalf of the declared exchanges. The contract is:

> "If you are Task 7 or 9, you will be given a list of exchange ids (or the attribute stored by the `use`) and you emit the appropriate function heads / capability tables inside the already-created `CcxtOcx.<Id>` modules."

The plan for 6b must leave clear extension points (a `@doc "Hook for Task 7"` or a small `emit_unified_methods/2` function that Task 7 will replace).
